### P2-15 compact 锁 unlink 竞态
审核确认两处缺陷，都实证复现了。除了方案说的 check/unlink 非原子，我另外抳到一个**方案没列的**：`_release_compact_lock()` 无条件删除，本进程锁若已超时被别人接管，释放时会把对方正在用的锁删掉——而这条每次 compact 结尾都走，比原竞态更容易触发。

修法：锁内写 token（pid + uuid4），删除前重新比对 token + inode。实测发现 **inode 会被复用**，光靠 inode 会漏判，两重校验缺一不可。递归也加了上界。

## 08:32-08:42 P1-5 完成 —— 方案里最后一个 P1 清零

### 问题
`context_safety_apply` 旧流程是先把新配置**写进正式文件**，然后才跑 validate。失败只把 `validateOk=False` 塞进返回值，无效配置原地留着。备份建了却从没人用它回滚。

实证复现：validate FAIL，20 项变更已落盘，正式配置带着新基线。这就是让 Gateway 起不来的那条路。

### 修法
候选配置先写临时文件校验（正好用上上一轮 P2-16 修通的 `OPENCLAW_CONFIG` 能力）→ 预校验失败就直接拒，正式配置一个字节都不碰 → 通过才备份 + 原子替换 → 写后再复验 → 失败立即回滚 → 回滚也失败就当独立高严重错误报（退出码 2）。

apply 现在默认 dry-run，真写要 `--execute-now`。

### 两处实测纠正了我最初的写法（这两个比修复本身更值得记）

**一、`_exclusive_lock()` 不可重入。** 我最初想得很周全，把整个流程包在锁里“锁内重读避免陈旧快照”。写完我没直接跑测试，而是先单独验了一下 flock 能不能嵌套——结果内层直接 ConfigWriteError 超时。若按我原想法提交，apply 一跑就死锁。

教训：不要靠推断 flock 语义，写完立刻实测。

**二、预校验不能把环境问题当非法。** 最初版本把 CLI 任何非零返回都当“候选配置非法”，结果测试环境下 CLI 读不到配置就报 FAIL——这会**永久堵死正常 apply**。现在只有 CLI 确实读到了我们的临时文件才判非法，否则降级为“预校验不可用”回退到写后复验。

这个缺陷是被既有测试 `test_validate_failure_propagated` 报红抳出来的——它本来不是为此写的。
