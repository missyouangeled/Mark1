## 15:59-16:24 Gateway drain + 上下文压缩死循环修复（点点要求）

点点反馈重启一直卡在 drain，误以为崩溃。诊断出 drain 卡住有三层原因，全部修复：

### 1️⃣ 深层根因：1M tokens 上下文导致压缩死循环 ✅
- 主会话 + dashboard 会话残留 `contextTokens: 1000000` + `modelOverride: glm-5.2`（glm-5.2 时代残留）
- 换回 128K doubao 后，Gateway 以为有 1M tokens 要压缩，128K 模型跑不动 -> 每次重启触发跑不完的嵌入式压缩，堵死 drain
- **修复**：清掉 sessions.json 所有 1M 残留和 glm-5.2 override；主会话（548 条消息全空，内容都在 7 个 compaction summary 里）重置为新 sessionId

### 2️⃣ 直接原因：drain 超时太长 ✅
- SIGTERM restart 的 drain timeout 默认 300s（由 `gateway.reload.deferralTimeoutMs` 控制）
- 配置 `deferralTimeoutMs: 120000` -> 日志验证 `timeout 300000ms` 变 `120000ms`，生效

### 3️⃣ 兜底：stuck session abort ✅
- 配置 `stuckSessionAbortMs: 120000`，stalled embedded run 2 分钟后主动 abort

### drain 完整机制（诊断结论）
1. drain 开始立即 `abortEmbeddedAgentRun(mode:"compacting")` 只中止压缩类 run
2. 等 `restartDrainTimeoutMs`(=120s) 等普通 run 自己结束
3. 超时后 `mode:"all"` 强制中止所有 run
4. systemd TimeoutStopSec=600s 兜底
- **关键认知**：每次在回复中途重启，当前回复本身就是个 active embedded run，会卡满 timeout——这是保护对话的正常设计，不是 bug

### 附带确认
