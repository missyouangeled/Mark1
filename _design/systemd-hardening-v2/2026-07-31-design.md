# Mark42 守护稳定性强化 — 设计方案 v1

> 触发背景：2026-07-31 08:30 发生 24 次 daemon-reload 链式 stop，导致 mark42 4 个守护
> 全停 ~8 分钟无人发现。已用 P1 防御（BindsTo + RefuseManualStop + StartLimit + verify）
> 修复，但还有 4 个候选改进方案未实施。本文档评估后给出推荐实施计划。

---

## 哲学：稳定靠"减依赖"不靠"加组件"

**原则**：每个新组件都是新故障源。Mark42 稳定性的第一性原理是
**"减少守护依赖 + 让 systemd 自己管"**，不是"加更多守护/工具"。

已通过 P1 修复（2026-07-31）覆盖 90% 的失效模式：
- BindsTo=openclaw-gateway.service（gateway 停则 mark42 停，gateway 启动则 mark42 自动启）
- RefuseManualStop=yes（拒绝外部 stop，防 reload 链式 stop）
- StartLimitBurst=5 + StartLimitIntervalSec=60（限频繁重启）
- install.sh 加 systemd-analyze verify（防语法错写错 unit）

剩余失效模式按"影响"分 3 层（详见 Q3 分析）。

## 4 个候选方案的真实价值

### 1. auditd

- **表面目标**：下次 24 次 reload 触发能追溯父进程
- **实际开销**：CPU +5-10% / disk 1-5GB/天 / auditd 自己维护 / 规则维护
- **实际价值**：**低**——systemd 自己有 LogLevel debug 机制，能记录 reload 触发链，零成本
- **替代方案**：`/etc/systemd/system.conf.d/override.conf` 加 `LogLevel=debug`（按需切换）

### 2. bash 主动记录（每日独立文件）

- **表面目标**：解决"当前会话命令不保存"
- **实际限制**：
  - bash history **只覆盖 interactive shell**（终端敲的命令）
  - exec 工具跑的非交互 bash **不记 history**
  - 所以"24 次 reload 触发者如果是 OpenClaw 内部脚本"——bash history **看不到**
- **可补的折中**：PROMPT_COMMAND——把 interactive shell 命令追加到 daily log
- **实际价值**：**中**——覆盖点点终端主动敲的命令（4 次 reload 如果是点点敲的，能记录）
- **daily 主动记**仍是**主路径**（覆盖贾维斯/点点双方主动记录）

### 3. OpenClaw 启动时 audit services 状态

- **表面目标**：守护悄悄死掉时快速发现
- **实际价值**：
  - OpenClaw 启动时记录 mark42 状态到 `~/.local/state/openclaw/mark42/audit/boot-$(timestamp).json`
  - watchdog 跑时对比基线，发现差异立即告警
  - 比 5 分钟 watchdog **快 5 分钟**捕获
- **风险**：基线对比逻辑复杂，**可能误报**（守护本来就不该启的状态）
- **可插拔设计**：`MARK42_AUDIT_BOOT=1` 启用，`0` 不跑

### 4. mark42 守护加 heartbeat 30s

- **表面目标**：缩短检测间隔从 5 分钟到 30 秒
- **实际价值**：
  - watchdog 5 分钟 = systemd 5 分钟 timer（一年 100K 次触发）
  - 30 秒 = 一年 1000K 次触发（10x 频繁）
  - 复杂度过高（要加 file watch / inotify）
  - **架构性问题**：gateway 死时 heartbeat 也没意义
- **结论**：**不做**——稳定性靠"守护不挂"不靠"挂得快发现"

## 推荐实施方案：分阶段

### 阶段 0：立即做（0 成本，最高价值）

**目标**：不引入新组件，只在已有机制上加强

#### 0.1 PROMPT_COMMAND 记录交互 shell 命令

**文件**：`~/.bashrc`（用户级）或 `/etc/bash.bashrc`（系统级）

**内容**：
```bash
# 【2026-07-31 Mark42 稳定性强化】记录交互 shell 命令
export PROMPT_COMMAND='history -a; \
  echo "[$(date +%H:%M:%S)] $(history 1 | sed "s/^[ ]*[0-9]*[ ]*//")" \
  >> ~/.openclaw/workspace/logs/bash-commands-$(date +%F).log 2>/dev/null'
```

**输出**：`~/.openclaw/workspace/logs/bash-commands-2026-07-31.log`
```
[09:08:42] ls -la
[09:08:55] systemctl --user status mark42-armor-guard
```

**覆盖范围**：点点在终端主动敲的所有命令

**不覆盖**：
- OpenClaw gateway 内部 exec 工具调用
- systemd timer / cron 跑的命令
- non-interactive bash（exec 工具跑的）

**风险**：0（log 追加写，append only）

**清理**：保留 30 天 = 30 个文件 × ~10KB = 300KB（可忽略）
- 加 `logrotate` 配置或 `find ... -mtime +30 -delete` 在 cron 里清

#### 0.2 systemd debug log 开关 — 【已分析后砍掉】

**重新评估结果：不实施**。

**原因 1：重启 user manager 才生效**
- `systemctl log-level` 只对 system manager（root）有效
- user manager 的 LogLevel 必须在 `/etc/systemd/user.conf` 或 `/etc/systemd/user.conf.d/` 改
- user manager 启动时才读这些配置 → **重启 user manager**（不现实）
- "按需切 debug"是伪命题

**原因 2：即使改了也查不到关键场景**
- systemd debug log 只记 **systemd 自身行为**（reload 是谁触发的）
- 如果触发者是 OpenClaw 内部脚本，**systemd 也查不到**（因为 OpenClaw 没调 systemctl）
- 如果触发者是点点终端命令，**0.1 PROMPT_COMMAND 已能查**（更精准）

**原因 3：PROMPT_COMMAND 验证证实 8:30 reload 触发者不在交互 shell**
- 验证 log 起始时间 9:17，无 8:30 记录
- 8:30 reload 触发者不是点点终端命令
- 8:30 触发者范围进一步缩窄

**结论**：0.2 是死路一条，砍掉。**0.1 已足够覆盖"能查到的范围"**。

### 阶段 1：3 个月内看效果再决定

**触发条件**：如果 3 个月内发现 mark42 守护"悄悄死过"但 P1 防御没拉起（理论上不应该），再考虑：

#### 1.1 启动 audit（条件性）

**触发条件**：openclaw boot health check 之后立刻 `mark42 status --json` 写基线

**实现**（**可插拔**）：
- `~/.openclaw/workspace/scripts/mark42-boot-audit.sh`（新文件，独立可卸）
- 用 `MARK42_AUDIT_BOOT=1` 启用（默认 0 = 不跑）
- 由 openclaw-boot-health-check.service 调用（在最后一步）
- 输出：`~/.local/state/openclaw/mark42/audit/boot-$(timestamp).json`

**watchdog 改造**：
- watchdog 跑时多一步：读上次基线，对比现在状态
- 如果发现守护丢失 → 立即写 broker event + 推 proactive-inject 通知
- 不重启守护（让 systemd 自己管）

**可插拔特性**：
- 不依赖 mark42 代码（独立脚本）
- 通过环境变量开关
- 日志可独立清理

**风险**：基线对比逻辑要小心（"守护不在"不等于"守护死了"——可能本来就没启）
- 建议：只对比 "active/running" → "dead" 的转换，不对比"不存在 → 存在"

---

### 阶段 2：不做

**heartbeat 30s** 不做。理由：
- watchdog 5 分钟 + P1 防御 + 启动 audit 已是充分覆盖
- 加倍频率 = 10x systemd 调度开销，**不解决问题只是缓解症状**
- 真要修 30s 检测不到的问题，应该查"为什么守护会死"（mark42 daemon 自身稳定性），而不是"加更多监控"

## 整体架构

```
┌─────────────────────────────────────────────────────────┐
│  OpenClaw Gateway (system unit)                          │
│  - 启动时跑 boot-health-check                            │
│    - 如果 MARK42_AUDIT_BOOT=1，调用 mark42-boot-audit.sh │
│      → 写 baseline.json                                   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  mark42 守护链（user unit，BindsTo=openclaw-gateway）    │
│  ┌──────────────────────────────────────────────────┐  │
│  │  bootstrap.service (oneshot)                      │  │
│  │  → 注册 4 个 loop 到 engine                       │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │  engine-daemon.service (simple)                   │  │
│  │  → 跑 4 个 loop（context-guard / health-watch    │  │
│  │    / memory-index / model-fallback）              │  │
│  │  → 写 daemon-heartbeat.json                       │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │  armor-guard.service (simple)                     │  │
│  │  → 每 5 分钟检查上下文压缩                       │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │  watchdog.timer (every 5 min) → watchdog.service  │  │
│  │  → 读 heartbeat.json + mark42 status             │  │
│  │  → 如果守护死 → service restart                  │  │
│  │  → 如果启动 audit enabled → 对比 baseline        │  │
│  └──────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘

故障检测路径：
- 守护死 → systemd Restart=always 拉起（10-15s 内）
- systemd 拉不起（外部干扰） → BindsTo 让父进程（gateway）重启时自动拉
- gateway 死 → mark42 跟着停（不浪费资源）→ gateway 重启时 mark42 必启
- 反复重启 → StartLimitBurst=5 限制（60s 内最多 5 次）

外部失效防御：
- 手动 systemctl stop → RefuseManualStop=yes 拒绝
- daemon-reload 链式 stop → RefuseManualStop=yes 仍生效
- 守护路径错（删 scripts/mark42.py）→ install.sh systemd-analyze verify 检测语法
- bash 命令不记录 → PROMPT_COMMAND 记录交互 shell 命令
- 关键操作不记 → daily 主动记（主路径）
- 8:30 那种 24 次 reload 查触发者 → systemd log-level debug 按需排查
```

## 风险评估

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| PROMPT_COMMAND 写 log 失败 | 低 | 丢命令记录 | 2>/dev/null 吞错 |
| LogLevel=info 漏掉关键信息 | 中 | 8:30 那种事件查不到 | 按需切 debug |
| 启动 audit 误报 | 中 | 假警报打扰 | 严格对比"运行中→死"转换 |
| 新组件成为新故障源 | 高 | 整体可靠性下降 | 阶段化实施，每步验收 |
